# H10/H12 Config-Intent Failure — Retrospective Analysis

**Date**: 2026-04-14
**Author**: Claude Code (with Shawn Ross)
**Related**: Obs 227 (retracted), Obs 230 (partially corrected), Obs 234 (retracted), Obs 235 (formal retraction), `~/.claude/projects/-home-shawn-Code-map-reader-llm/memory/feedback_config_intent_verification.md`

---

## Executive summary

The preregistered H10 (Training Pool Size) and H12 (HP:HN Ratio) experiments were run across five `pool_160_*` configurations on 2026-04-11 and generated ~$33 of API spend. The intent was to test **image-based few-shot library calibration**: hard-positive and hard-negative example crops, mined by a diversity-optimised selection process, would be sent to the proposer as reference images to test whether hard-example curation improves detection performance.

The configs actually used were auto-generated from `detect_brief-text`, a **text-only** proposer configuration with `include_example_images: false`. Under that flag, `scripts/4_detect_mounds_batch.py:816` **skips the entire example loop** — no images, no labels. The 17-example library per pool was never transmitted to the API. The `library_hash` difference between pools was bookkeeping only.

The experiment thus varied a factor that was not physically transmitted to the model. The preregistered H10 and H12 questions were not tested. The "null results" documented in Observation 227 (2026-04-12) and the "+0.07 F1 library effect" documented in Observation 234 (2026-04-14) are both tautological consequences of varying a non-transmitted parameter and have been retracted.

The failure was caught when Shawn asked a first-principles question on 2026-04-14: *"if H10 was text-only, what were the 'hard examples'?"* A one-minute config-file check would have answered that question before any API spend was committed.

**This document serves two purposes**: to externalise the failure analysis as a standalone artefact, and to seed the rules and infrastructure changes that should prevent this class of error in future. It is a post-mortem, not a punishment — the goal is structural prevention, not blame.

## Technical root cause

### Code path — where the modality flag silently invalidates the experiment

```python
# scripts/4_detect_mounds_batch.py:800-830 (paraphrased)
examples = config.get("examples", [])
include_example_images = config.get("include_example_images", True)
# ...
if not include_example_images:
    print("Text-only modality: skipping example images")
    example_count = 0
else:
    example_count = 0
    for ex in examples:
        label = ex.get("label", "Example")
        path_str = ex.get("path", "")
        img_path = examples_dir / path_str
        if img_path.exists():
            reference_parts.append(types.Part.from_text(text=label))
            with open(img_path, "rb") as f:
                image_bytes = f.read()
            reference_parts.append(
                types.Part.from_bytes(data=image_bytes, mime_type=mime_type)
            )
            example_count += 1
```

When `include_example_images` is `False`, the entire `else` branch is skipped. No text labels, no image bytes, nothing from the `examples` list reaches `reference_parts`. The resulting API payload contains only:

1. The system instruction (`detect_brief-text.md`)
2. The tile image
3. Generation config (temperature, thinking level, etc.)

Every H10/H12 pool variant produces **exactly this payload**, with no variation between pools. The `library_hash`, `pool_source`, and `examples` fields in the config are processed, hashed, and recorded in `run.meta.json` — but the *contents* of those fields never influence the API call.

### Configuration inheritance — where the flag came from

`scripts/build_example_pool.py` auto-generates configs for each pool by cloning `detect_brief-text.json` and replacing the `examples` list with pool-specific entries. It does not override `include_example_images`. Since the base `detect_brief-text.json` has:

```json
{
  "version": "detect_brief-text",
  "description": "H1 baseline. M/E=Brief-text (no images), H5=Minimal, canonical-first ordering.",
  "hypothesis": "H1",
  "include_example_images": false,
  ...
}
```

…the auto-generated pool configs inherited `include_example_images: false`. The description even says *"no images"*. The `hypothesis` tag says `H1`, not `H12`. The auto-generator never questioned why a library-composition experiment was cloning a text-only baseline.

The fix is one line in `build_example_pool.py`: set `include_example_images: true` when generating a pool config for an H12-class experiment, or use `detect_brief-text-image.json` as the base instead. Either would have produced a correct payload.

### The HP/HN crops existed but weren't plumbed in

The H10 example pools are real image files:

```
outputs/h10/example-pools/pool_160_hp4hn4/
├── crops/
│   ├── hp_01.png  (128×128 hard positive crop)
│   ├── hp_02.png
│   ├── hp_03.png
│   ├── hp_04.png
│   ├── hn_01.png  (128×128 hard negative crop)
│   ├── hn_02.png
│   ├── hn_03.png
│   └── hn_04.png
├── pool_metadata.json
└── selected_examples.json
```

These 128×128 PNGs were mined by `build_example_pool.py` using a diversity-optimised selection on the 160-tile H10 calibration pool. They contain real hard examples (kurgans with low consensus scores, triangulation points confusable for mounds, etc.). But the auto-generated config referenced them via abstract paths (`neutral-naming/example_01.png` through `example_17.png`) that were copied into `prompts/configs/h10/examples/pool_160_*/neutral-naming/` — and then the `include_example_images: false` flag meant none of them were ever loaded or sent.

**The failure is not that the library was built wrong. The library was built correctly. The failure is that the library was built for an image-based experiment and then connected to a text-only proposer.**

## Why it wasn't caught earlier

### The "surprising results trigger verification" rule didn't fire for Obs 227

The project's `CLAUDE.md` instructs:

> **Flag surprising results.** When analysis produces results that contradict expectations, hypotheses, or prior experience, proactively raise this with the user... (1) Flag the surprise explicitly, (2) Verify the data pipeline is correct (are we analysing what we think we're analysing?), (3) ... document the finding as a genuine scientific result worth explaining.

Obs 227's headline was *"H10/H12 null results — verifier architecture dominates library composition"*. This finding was **not surprising**. It matched the project's existing [Diversity Taxonomy](../../.claude/projects/-home-shawn-Code-map-reader-llm/memory/MEMORY.md) (in which parametric interventions like library variants are consistently null) and extended the pattern that "architecture > prompt wordsmithing". A reader who already believed library composition didn't matter would read Obs 227 as confirming their model.

Because it wasn't surprising, step (1) didn't fire — and steps (2) and (3) ran without a sanity check. The pipeline-correctness verification is only triggered by surprise. Non-surprising results slipped through the guardrail.

**This is the deepest lesson from the failure**: *the "flag surprising results" rule has a blind spot for comfortable findings*. A null result that fits the prior model is more dangerous than a shocking positive result, because the prior model provides cover against verification. A proper scientific protocol would require verification regardless of whether the finding is surprising.

### Obs 234 was surprising but I skipped the verification step anyway

When I wrote Obs 234 on 2026-04-14, I explicitly flagged the finding as surprising (*"H10 pool dominates canonical by +0.07 F1 — paper headline should be revisited"*). Step (1) of the rule fired. I then moved directly to step (3) — documenting the finding and its implications — without running step (2).

The verification I should have done:

```bash
grep include_example_images prompts/configs/h10/detect_pool_160_hp4hn4.json
# → "include_example_images": false
```

Ten seconds of work would have collapsed the entire "library effect" story into "the library wasn't being sent, so there can't be a library effect; what's really going on?" That is exactly the line of investigation Shawn's question prompted the next session — three hours later — when it should have been triggered by my own protocol.

**Why did I skip it?** Honestly, because I had an explanation ready. The mechanism I proposed ("H10's HP:HN calibration mined better hard examples than the canonical library") was plausible, internally consistent, and matched the data. Having a good explanation in hand reduced my felt need to verify the upstream pipeline. *Explanation availability acted as a substitute for evidence.*

The CLAUDE.md rule addresses this explicitly: *"not to explain it away or accept it uncritically"*. I explained it away.

### Inherited findings are under-verified

Obs 234 was not a first-principles finding. It was a *combination* of my own fresh analysis with Obs 227's inherited framing. I read Obs 227's "H10/H12 null results" heading, accepted the premise that the H10 data was meaningfully testing library composition, and built my +0.07 claim on top of that premise.

Inheriting a premise from a prior session is different from deriving a premise from the data. **Inheritance skips verification by default**, because the prior session has already written the explanation in a place that looks authoritative (a working-notes observation, a memory file). The new session reads the explanation, updates its internal model to match, and proceeds.

This is structurally similar to how propagated belief works in science: a paper cites a prior finding, a reviewer accepts the citation without re-verifying, the prior finding becomes "known" by citation momentum rather than by re-testing. Claude Code sessions exhibit the same pattern at compressed timescales: Obs 227 was cited implicitly by my 2026-04-14 session, and its premise became "known" by inheritance.

The correct rule is: **when a new session builds on an inherited observation that's about to influence a decision, the first step should be to re-verify the inherited observation's premise**. This is the "inheritance scepticism" rule added to `feedback_config_intent_verification.md`.

### Non-surprise + inheritance = worst case

The dangerous combination is an *inherited non-surprising finding*. Obs 227 was both:

1. **Non-surprising** (it fit the project's diversity taxonomy)
2. **Inherited** (written by a prior session)

Both failure modes operated simultaneously. The prior session didn't verify because the finding wasn't surprising. My session didn't verify because I was inheriting, and because the finding was still not surprising to me.

A new session encountering a fresh surprising finding triggers at least one of the guardrails. A new session encountering an inherited non-surprising finding triggers neither. **This is the regime in which errors propagate silently across sessions.**

## Failure modes, enumerated

### Claude-side failure modes

1. **Pipeline verification skipped for comfortable findings.** The CLAUDE.md "flag surprising results" rule has a blind spot for non-surprising findings. Obs 227's non-surprise let it bypass verification.
2. **Pipeline verification skipped for surprising findings when an explanation is available.** I had a plausible story ("H10 library is better calibrated") that substituted for evidence. The CLAUDE.md rule was half-followed: surprise flagged, verification omitted.
3. **Inherited observations trusted by default.** Obs 227 was cited implicitly by my Obs 234 without re-verification of its premise.
4. **Config-file contents unexamined at launch or at interpretation time.** A `grep include_example_images` on any of the 5 H10 config files at any point in the three days would have caught the mismatch.
5. **Hypothesis-tracker cross-check absent.** H12's preregistered question required `include_example_images: true`. This is documented in the preregistration. No one (not earlier CC, not me) read the preregistration entry and compared it to the config in use.
6. **Auto-generated artefacts trusted without reading.** `build_example_pool.py` produced the pool configs. I assumed the generator was doing the right thing and never read the generated configs to check.

### Code-side failure modes

1. **Auto-generator doesn't enforce hypothesis-required fields.** `build_example_pool.py` can produce a no-op config for H12 without any warning or block. A hypothesis-aware generator would refuse.
2. **No launch-time README or self-audit.** Nothing in the pipeline writes an "experimental intent" document at launch time that could be checked against the actual meta.json.
3. **No pre-run config diff.** Before launching a batch of configs, the pipeline could diff each config against its base and print the differences — which would have surfaced the missing modality override.
4. **No dry-run payload inspection.** A `--dry-run` mode that prints the shape of the first API payload (number of parts, size of reference_parts, instruction length) would reveal an empty example set instantly.
5. **Meta.json doesn't record whether examples actually reached the model.** The meta records `include_example_images: false` and `example_count: 17` as two separate fields — a reader could easily interpret `example_count: 17` as "17 examples were sent". The meta should record `examples_transmitted: 0` explicitly when the flag is false.

### User-side considerations (mild, not really failures)

Shawn's own suggestion — include modality in the API-gate proposal — is the most concrete user-side improvement. Additional suggestions:

1. **Experiment-launch intent statement.** A one-liner at launch naming the hypothesis, the varied factor, the transmission mechanism, and the base config. Example: *"H12 test. Varying HP:HN ratio in the few-shot library. Ratio is transmitted via the `examples` field when `include_example_images: true`. Base config: detect_brief-text-image.json."* This sentence has three verifiable anchors.
2. **Modality-explicit experiment names.** "H12 pool run" is ambiguous; "image+text H12 pool run" or "text-only H12 pool run" disambiguates at a glance. The modality name is a mnemonic; the hypothesis ID is not.
3. **Pre-run dry-run approval.** Request a dry-run config read + payload preview before spending money on the real batch. 30 seconds of check at the gate.

None of these are things Shawn "should have done". The failure was upstream of the user side. These are offered as structural redundancies, not as user-fault corrections.

## Rules added to prevent recurrence

Five rules have been added to `feedback_config_intent_verification.md`:

1. **Config sanity check before every API gate.** State modality, temperature, thinking, K, instruction hash, library hash (and whether the library will physically reach the model) in every API-spend proposal.
2. **Mechanism verification before writing up any effect ≥ 0.02 F1.** State the causal chain explicitly. Verify the factor is physically present in the API payload. Include the verification evidence in the observation body.
3. **Hypothesis-tracker cross-check for H-tagged experiments.** Read the preregistration entry for the hypothesis. Confirm the config manipulates the hypothesis's factor. Block the launch if not.
4. **Modality-explicit config names in launch requests.** "Image+text K=5 detect_brief-text-image" rather than "K=5 H12 pool run".
5. **Inheritance scepticism across sessions.** When building on an observation inherited from a prior session, re-verify its premise before proceeding. Non-surprise is not evidence of correctness.

These five rules are encoded in the feedback memory and will surface automatically at session start.

## Code-side fixes proposed (awaiting implementation)

Three infrastructure changes would structurally prevent this class of error:

### Fix 1 — Hypothesis-tagged config generation with enforced required fields

**Change**: `scripts/build_example_pool.py` (and any other auto-generator that produces hypothesis-tagged configs) should read the target hypothesis's required config fields from the preregistration and refuse to emit a config that doesn't satisfy them.

**Concrete implementation**: a small lookup table keyed by hypothesis ID:

```python
HYPOTHESIS_REQUIREMENTS = {
    "H1": {"include_example_images": [True, False]},  # varies modality
    "H7": {"varies": "temperature"},
    "H8": {"include_example_images": True},  # must transmit library
    "H12": {"include_example_images": True}, # must transmit library
    # ... etc.
}
```

When `build_example_pool.py` is called with `--hypothesis H12`, it checks the base config against the requirement and either (a) overrides the field automatically with a warning, or (b) errors out with a clear message asking for the correct base config.

**Leverage**: highest. Structurally prevents the same error from happening again for any hypothesis with a mechanically-checkable requirement.

### Fix 2 — Launch-time README writer

**Change**: Every experiment output directory (`outputs/<experiment>/`) should have an auto-written `README.md` at launch time that states:

- Hypothesis ID and one-line description
- Base config used, and its modality flag
- Factor being varied, and the config field that carries it
- Verified values of the modality flag, temperature, thinking level, K
- A one-line claim that the factor *will* reach the model (or a warning that it won't)

**Concrete implementation**: add a `write_experiment_readme()` call to `4_detect_mounds_batch.py`'s launch path. Template:

```markdown
# Experiment: {experiment_name}
**Hypothesis**: {hypothesis_id} — {hypothesis_description}
**Base config**: {config_path}
**Varied factor**: {factor_name} via `{config_field}`
**Modality**: `include_example_images={value}` ({sent_or_not})
**K**: {k_passes} passes
**Temperature**: {temperature}
**Thinking**: {thinking_level}
**Launched**: {timestamp}
**Git commit**: {commit_hash}

## Will the varied factor reach the model?
{yes_or_no_with_explanation}
```

The README is both documentation and a self-audit: if the claim in the README is contradicted by the actual meta.json after the run completes, the launcher has a bug.

**Leverage**: medium-high. Makes the config-intent explicit and human-readable. A post-run audit would catch mismatches. Also useful for archival / reproducibility purposes unrelated to this failure.

### Fix 3 — Pre-run config diff against base

**Change**: When launching a batch of configs that are variants of a base, print a diff between each variant and its base, showing only the fields that changed. Warn loudly if the diff includes *only* fields that are no-ops given the other fields.

**Concrete implementation**: add a `diff_against_base()` check in the launch path. For H10/H12 the output would have been:

```
=== Config diff: detect_brief-text_pool_160_hp4hn4.json vs detect_brief-text.json ===
  version: "detect_brief-text" → "detect_brief-text_pool_160_hp4hn4"
  library_hash: "8580ecb2..." → "a168f1cc..."
  examples[0..16]: 17 entries changed

  ⚠️ WARNING: Changed fields ({library_hash, examples}) are no-ops
  when `include_example_images: false` (inherited from base).
  The varied factor will not reach the API payload. Proceed anyway? [y/N]
```

This is the cheapest fix — a single tool invocation with a clear warning — and would have blocked the H10/H12 launch at the exact right moment.

**Leverage**: high, cheap to implement. Also useful as a general sanity check for any config batch.

## What IS still valid from the H10/H12 experimental arm

Not all the work was wasted. The following artefacts survive the retraction because they do not depend on the library being transmitted:

1. **WBF Variant C parameter calibration** (Obs 228, Obs 229). The IoU threshold, min-separation radius, vote-aware anchor threshold, and box size filters were calibrated using hp4hn4 data, but the parameters themselves are library-agnostic. WBF is a post-hoc aggregation method that operates on raw per-pass detection geojsons; it doesn't care what prompted the detections.

2. **WBF-vs-greedy aggregation comparison** (Obs 230, statistically equivalent, p=0.60). This is a test of aggregation method, not of library composition. Both conditions saw the same underlying per-pass detections, so the comparison isolates aggregation. The "on hp4hn4" framing is meaningless for the aggregation question, but the comparison itself is valid.

3. **327-tile evaluation universe.** The `inputs/vectors/bounds/384/h10_test_bounds.geojson` file defining the 327-tile subset is a useful common denominator for leaderboard evaluation, even though the 160 excluded calibration tiles turned out not to affect the text-only proposer.

4. **Per-pass detection counts at K=10 on 327 tiles.** Redundant with existing K=30 sweeps but provides a reproducibility cross-check.

5. **Tile-set hygiene principle.** The design instinct — exclude training/calibration tiles from evaluation to prevent data leakage — is still correct even though the specific leakage was avoided trivially (the calibration data never reached the model).

6. **The retrospective itself.** The rules and code fixes triggered by this failure will plausibly save more than $33 of future API spend and prevent more than 2 future observations from being retracted. The structural value of "now we have a verification protocol" exceeds the cost of "we wasted $33 to learn that we needed one".

**Net accounting**: roughly two-thirds of the H10/H12 work survived as productive output (WBF methodology, evaluation universe, reproducibility cross-check, protocols). Roughly one-third was directly wasted (the H12 test itself, plus 3 hours of downstream analysis across 3 sessions that had to be unwound).

## Lessons that generalise beyond this project

### 1. Surprise-triggered verification has a blind spot for comfortable findings

The CLAUDE.md rule *"verify the pipeline when results are surprising"* is necessary but insufficient. Non-surprising results slip through the guardrail precisely because they don't trigger it. A complete rule needs a second trigger: **verify the pipeline when the result is about to be cited as evidence, regardless of whether it's surprising**. Non-surprise is not evidence of correctness.

### 2. Explanation availability substitutes for evidence

When a plausible mechanism is ready to hand, the felt need to verify the evidence drops. This is a general human cognitive bias (Kahneman's "WYSIATI" — "what you see is all there is") that Claude Code exhibits too. The counter-rule: *a ready explanation is a reason to verify the evidence harder, not less*. A good-feeling explanation for a surprising result is exactly the configuration in which errors hide.

### 3. Inheritance across sessions compounds errors silently

In any long-running project with memory handoff between sessions, inherited findings should be treated as un-verified by default. The prior session's framing is a hypothesis, not a fact. The cost of re-verification on first use is cheap (minutes); the cost of compounding an error across sessions is expensive (hours of unwinding, plus scientific credibility risk).

### 4. Library-hash computation ≠ library transmission

This is a specific technical gotcha for LLM-based pipelines where example libraries are fed via few-shot prompts. The pipeline may compute a hash over the library contents for caching or deduplication purposes, producing a per-library hash that *looks* like provenance but doesn't confirm transmission. Always verify transmission at the API-payload level, not at the library-artefact level.

### 5. Auto-generated configs inherit their base's assumptions

Any configuration generator that clones a base and modifies specific fields inherits every *unchanged* field from the base. If the base has a default that the generator doesn't override, the default silently propagates into contexts where it was never intended. The fix is to make generators *hypothesis-aware*: know what fields the target use-case requires, and enforce those requirements against the base, not the other way around.

### 6. "The data exists" ≠ "the data answers the question"

This is the generalised version of the specific H10/H12 failure. The run completed, the output files are on disk, the meta.json is parseable, the numbers look reasonable — all of these are true *and* orthogonal to whether the data answers the preregistered question. Verification needs to include the semantic question: *"does the execution actually test the intent?"*

### 7. One-minute config checks are the highest-leverage action in experimental science

The H10/H12 failure would have been prevented by any of:

- 10 seconds: `grep include_example_images <config>`
- 30 seconds: read the config file and the base config
- 1 minute: diff the config against its base and flag no-op-field changes
- 5 minutes: read `4_detect_mounds_batch.py:816` and trace the code path

Meanwhile, the cost of the failure was:

- ~$33 API spend
- 3 hours across 3 Claude Code sessions
- Two observations retracted
- A near-miss on a paper headline

**Ratio of prevention cost to failure cost: ~1:1000**. Cheap sanity checks are the single highest-leverage action in experimental science. The instinct to "just run it and see" should always be dominated by a 30-second precondition check.

### 8. Self-reported protocol adherence is unreliable

CLAUDE.md contains the protocol that would have caught this failure (the "flag surprising results → verify pipeline" rule). Both sessions knew the rule. Both sessions failed to apply it. **Protocols held in prose are not self-enforcing**; they need structural backing — code-side fixes, launch-time blocks, mandatory verification outputs — to actually run. The five feedback rules are an improvement but still rely on my discipline. The three code-side fixes (hypothesis-aware generator, launch-time README, pre-run config diff) move enforcement from discipline to infrastructure, which is where it belongs.
