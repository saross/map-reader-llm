## Spatial Tolerance

**Primary matching threshold: 20 metres**

A detection is considered a **true positive** if it falls within 20m of a ground truth reference point. This is implemented by buffering reference points and checking for intersection with detection points.

**Spatial tolerance curve: [10, 20, 30, 50] metres**

The evaluation also generates a spatial tolerance curve showing how precision, recall, and F1 vary across different buffer distances:

| Buffer (m) | Purpose |
|------------|---------|
| 10 | Strict localisation |
| 20 | Default threshold |
| 30 | Moderate tolerance |
| 50 | Lenient tolerance |

The 20m default was chosen as a reasonable balance - it accounts for:
- Georeferencing imprecision in historical maps
- Symbol centroid ambiguity (mound symbols can be 10-20m across at 1:50,000 scale)
- Ground truth digitisation variation

Let me analyze the detection matching algorithm:

**Current approach** (lines 89-105 of `lib_advanced_metrics.py`):

1. Buffer each reference point by 20m
2. **TP counting**: Spatial join finds all detection-reference intersections, then counts unique *reference* indices
3. **FN counting**: References with no matching detection
4. **FP counting**: Detections that don't intersect any buffered reference

**Assessment**: This is a **reference-centric** approach:
- Each reference can only contribute 1 TP (even if 3 detections hit it)
- A detection hitting multiple references counts all as matched (not double-counted as FPs)
- No explicit one-to-one constraint

This is similar to PASCAL VOC evaluation and is reasonable for our use case. The main edge case is if one detection spans two nearby mounds - both count as found, which seems correct (we care about finding mounds, not penalising imprecise localisation).

**Recommendation**: Document this as "reference-centric matching" rather than "nearest spatial match". It's rigorous for our purposes.

Example-level analysis asks: **which specific examples in your library drive performance, and how do they interact?**

## What You Could Learn

| Question | Insight |
|----------|---------|
| Which examples have high marginal value? | "Hard negative #3 (benchmark alone) reduced FPs by 12% when present" |
| Which examples are redundant? | "Hard negatives #2 and #5 are interchangeable; including both adds nothing" |
| Are there harmful examples? | "Ambiguous example #7 actually *hurts* precision — model becomes uncertain" |
| Do examples interact? | "Hard negative X only helps when canonical positive Y anchors the schema" |

## Analysis Approaches

### 1. Simple Ablation (Leave-One-Out)

Run N configurations, each omitting one example. Measure performance drop.

```
Full library:        F1 = 0.72
Without hard_neg_3:  F1 = 0.65  → high value (+0.07)
Without hard_neg_5:  F1 = 0.71  → low value (+0.01)
```

**Pros**: Simple, interpretable  
**Cons**: Misses interactions; requires k+1 runs for k examples

### 2. Balanced Incomplete Block Design (BIBD)

A statistical design where:
- Each example appears in exactly *r* of *N* passes
- Each *pair* of examples appears together in exactly *λ* passes

This enables ANOVA-style decomposition:

```
Performance = μ + Σ(example main effects) + Σ(pairwise interactions) + ε
```

**Example**: With 10 examples and 30 passes, you could ensure each example appears in exactly 15 passes, and each pair co-occurs in ~7 passes.

**Pros**: Statistically principled; detects interactions  
**Cons**: Requires upfront design; constrains your experimental structure

### 3. Regression on Example Presence

Model performance as a function of which examples were included:

```
F1 ~ β₀ + β₁(ex1) + β₂(ex2) + ... + βₖ(exk) + ε
```

Each βᵢ estimates the contribution of example *i*. With enough passes and random sampling, you get stable estimates.

**Pros**: Works with any sampling scheme; easy to extend to interactions  
**Cons**: Requires sufficient coverage of the combinatorial space

### 4. Shapley Values

From game theory: measures each example's marginal contribution averaged across *all possible subsets*.

```
Shapley(exᵢ) = weighted average of [F1(S ∪ {exᵢ}) - F1(S)] 
               across all subsets S not containing exᵢ
```

**Pros**: Theoretically principled; handles interactions implicitly  
**Cons**: Computationally expensive (2^k subsets); often approximated

## Practical Recommendation

Given you're building the library empirically and don't know the size yet:

1. **Design for flexibility**: Use frequency-capped random sampling (as discussed), but **record exactly which examples appeared in each pass**

2. **Post-hoc regression**: After experiments, fit:
   ```
   F1_pass ~ β₀ + Σ βᵢ(exampleᵢ_present) + ε
   ```
   This works with any achieved design and tells you which examples mattered.

3. **If library is small (≤10)**: Consider a proper BIBD upfront — the statistical power gains are worth the design effort.

4. **Report coefficients**: "Hard negative examples contributed +0.05 F1 on average (β = 0.05, SE = 0.01); canonical positives contributed +0.08"
